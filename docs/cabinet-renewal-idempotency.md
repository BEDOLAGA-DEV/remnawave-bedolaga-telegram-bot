# Повторные запросы продления в кабинете

Бэкенд и кабинет с этим изменением обновляются вместе. Миграция `0141` создаёт
`subscription_renewal_operations`. Клиент `POST /cabinet/subscription/renew`
передаёт `operation_id` (UUID), `expected_end_date` (исходный срок подписки с часовым
поясом), `period_days` и идентификатор подписки. Старый запрос без новых полей
отклоняется валидацией до списания.

Клиент сохраняет идентификатор для сочетания подписки, периода и исходного срока
и использует его при повторе после ошибки сети. Сервер блокирует сначала владельца,
затем подписку. Ответ операции записывается в одной транзакции с уменьшением баланса,
увеличением срока и финансовой транзакцией. Повтор возвращает сохранённый ответ;
изменение параметров того же идентификатора отклоняется с HTTP 409. Запись операции
принадлежит владельцу и не даёт доступа к ответам других пользователей.

Разные идентификаторы из двух вкладок защищены проверкой `expected_end_date`:
после первого продления устаревший запрос получает 409 без списания. Для намеренного
следующего продления нужно загрузить обновлённую подписку. Если браузер не разрешает
хранение данных, проверка исходного срока всё равно предотвращает повторное списание,
но после перезагрузки вкладки прежний ответ может быть недоступен клиенту без старого UUID.

После нехватки баланса оба поля сохраняются в корзине. Автовыполнение такой корзины
проходит тот же путь, что ручное продление. Старые корзины кабинета без идентификатора
не выполняются автоматически: пользователь должен повторно подтвердить покупку
в обновлённом кабинете. Корзины других сценариев этим контрактом не меняются.

Записи результата не имеют короткого TTL: очистка Redis и перезапуск приложения
не должны снимать защиту от повтора. Миграция не изменяет баланс или подписки.
Синхронизация панели и уведомления остаются после финансового коммита; возврат прежнего
ответа не запускает их повторно. Это защита финансовой операции, а не гарантия доставки
каждого внешнего уведомления ровно один раз.
