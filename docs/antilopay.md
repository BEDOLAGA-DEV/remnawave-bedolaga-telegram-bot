# Antilopay

Контракт: [официальная документация Antilopay](https://doc.antilopay.com/AntilopayAPI.pdf), разделы 3.3, 5.1–5.2, 10. Проверен 2026-10-27.

## Создание счёта

- Используются `POST https://lk.antilopay.com/api/v1/payment/create` и `payment/check`.
- Валюта запроса и локального счёта — `RUB`. Сумма API — число рублей с точностью до копейки; отрицательные, нечисловые и дробные копейки не допускаются.
- JSON подписывается RSA/SHA256; подпись соответствует отправленным UTF-8 байтам. Заголовки: `X-Apay-Secret-Id`, `X-Apay-Sign`, `X-Apay-Sign-Version: 1`.
- HTTP 200 недостаточно: требуется `code: 0`. Создание также требует непустого `payment_id` и HTTPS `payment_url`. HTTP-редиректы и автоматическое повторение POST создания запрещены.
- Карта → `CARD_RU`, СБП → `SBP`, SberPay → `SBER_PAY`.
- Действуют настройки доступности, лимитов и вариантов оплаты кабинета. Наличие Telegram ID для оплаты из кабинета не требуется.

Antilopay требует email или телефон покупателя. Подстановка общего выдуманного email удалена. Бот запрашивает email после суммы, если у аккаунта его нет; кабинет показывает поле email с адресом аккаунта по умолчанию. Этот контакт используется только для платежа и не меняет учётную запись. API кабинета принимает необязательное поле `customer_email` и использует email аккаунта как запасной вариант.

Гостевой платёж использует email из контакта покупки либо аккаунта покупателя. Без реального контакта счёт не создаётся. Для анонимной покупки с Telegram-контактом нужно выбрать контакт email; фиктивного адреса для обхода требований API нет.

## Уведомления и зачисление

Локальный заказ и его метаданные фиксируются **до** запроса к Antilopay. Поэтому раннее подписанное уведомление уже находит заказ. Привязка ответа создания не перезаписывает результат раннего зачисления.

Подпись `X-Apay-Callback` проверяется по исходному телу запроса публичным ключом проекта. Для зачисления нужны совпадающие `order_id`, `payment_id` (если уже привязан), `currency` и точный `original_amount`. Поле `amount` — сумма после комиссии, для зачисления покупателю не используется. Отсутствующее значение, неверная валюта или разница даже в одну копейку не дают пополнить баланс.

Подтверждение оплаты, транзакция и баланс фиксируются вместе. Обработчики блокируют пользователя, затем платёж; повторные и конкурентные уведомления не увеличивают баланс повторно. Ошибка до фиксации вызывает rollback.

Для корректно подписанных уведомлений обработчик сохраняет HTTP 200 согласно разделу 10.3 документации. Потерянное или не обработанное уведомление восстанавливается через `payment/check`: ручная и фоновая проверки используют тот же обработчик зачисления. Фоновая проверка подчиняется общей настройке автопроверки и её окну поиска платежей; не является бесконечным архивным сверщиком. При неоднозначной сетевой ошибке создания локальная запись остаётся для проверки по `order_id`; повторный POST автоматически не отправляется.

Несовпадение суммы/валюты требует разбора оператором. Автоматический возврат денег, обработка финансового спора и рекуррентные списания в это исправление не входят. Параметры фискализации конкретного мерчанта, включая обязательный `vat` для ОСНО, требуют отдельной настройки; наличие успешных локальных проверок не подтверждает настройки мерчанта в Antilopay.

## Проверки

- `tests/services/test_antilopay_service_contract.py`: версия, валюта, RSA-подпись, суммы, контакт, ответы API.
- `tests/services/test_antilopay_callback_contract.py`: недостоверные поля подтверждения не дают зачислить деньги.
- `tests/services/test_antilopay_contact.py`: запрос контакта в боте и метаданные гостевой покупки.
- `tests/cabinet/test_balance_topup_provider_contract.py`: подспособы, лимиты, права и контакт кабинета.
- `tests/database/test_antilopay_lifecycle_postgres.py`: настоящий локальный HTTP, RSA-уведомление, PostgreSQL; бот/кабинет × карта/СБП/SberPay × раннее уведомление/опрос/конкурентные уведомления. Внешний провайдер локальный, реальные деньги не используются.

Обновлять бот и кабинет вместе для поля контакта. Миграция БД не требуется.
