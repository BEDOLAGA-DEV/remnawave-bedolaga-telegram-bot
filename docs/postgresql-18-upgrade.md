# Обновление PostgreSQL 15 → 18

С версии, содержащей это изменение, `docker-compose.yml` использует
`postgres:18-alpine` вместо `postgres:15-alpine`.

## Зачем

- **Окно поддержки.** PostgreSQL 15 перестанет получать обновления в ноябре
  2027 года; PostgreSQL 18 поддерживается до ноября 2030-го. Переезд «через
  версию» позже станет только болезненнее.
- **Производительность.** PG 18 принёс подсистему асинхронного I/O
  (`io_method` = worker по умолчанию, `io_uring` на Linux) — ускоряет
  seq scan, VACUUM и bitmap heap scan на I/O-нагрузках; skip scan для
  составных B-tree-индексов (запросы по «хвостовым» колонкам индекса без
  ведущей — у бота таких композитных индексов много); быстрее выполняется
  VACUUM; статистика планировщика теперь переживает pg_upgrade — после
  апгрейда не будет периода «тупых» планов.
- **Функциональность.** Нативный `uuidv7()`, виртуальные generated columns,
  temporal-ограничения, OAuth-аутентификация.
- Бот работает через SQLAlchemy 2 + asyncpg — обе библиотеки полностью
  поддерживают PG 18. Вся цепочка alembic-миграций проверена на чистых
  PG 15.16 и PG 18.4.

## ⚠️ Сменилась точка монтирования тома

В официальном образе `postgres:18+` каталог данных переехал:
`VOLUME` теперь `/var/lib/postgresql` (раньше `/var/lib/postgresql/data`),
а `PGDATA` — `/var/lib/postgresql/18/docker`. Сделано это ради поддержки
`pg_upgrade` между мажорными версиями. Наш compose уже обновлён; если у вас
кастомный compose — обязательно поменяйте маунт, иначе данные окажутся вне
тома и пропадут при пересоздании контейнера.

## Новые установки

Ничего делать не нужно — `docker compose up -d` поднимет PG 18.

## Обновление существующей установки

Каталог данных PG 15 несовместим с PG 18 напрямую (контейнер не стартует
с «database files are incompatible with server»). Надёжный путь — дамп и
восстановление:

```bash
# 1. Остановить бота (Postgres оставить работать)
docker compose stop bot

# 2. Полный дамп СТАРЫМ (15-м) контейнером
docker compose exec postgres pg_dumpall -U ${POSTGRES_USER:-remnawave_user} > backup_pg15.sql

# 3. Обновить код (новый compose), убрать старый контейнер и том
docker compose down postgres
docker volume rm <имя_проекта>_postgres_data

# 4. Поднять PG 18 и восстановить дамп
docker compose up -d postgres
# дождаться healthy:
docker compose ps postgres
cat backup_pg15.sql | docker compose exec -T postgres psql -U ${POSTGRES_USER:-remnawave_user} -d postgres

# 5. Запустить бота
docker compose up -d bot
```

Дамп со стороны 15-го сервера его же клиентом — штатный сценарий
(`pg_dumpall` совместим «вперёд»: дамп 15 восстанавливается в 18).
Перед процедурой не помешает дополнительно сделать бэкап из самого бота
(админ-меню → Бэкапы).

Примечания:

- В PG 18 `initdb` включает контрольные суммы данных по умолчанию — это
  штатно и полезно (раннее обнаружение повреждений на диске).
- `pg_dump`, запускаемый ботом для бэкапов (если установлен в PATH), должен
  быть версии ≥ 18, чтобы дампить 18-й сервер. В официальном образе бота
  pg_dump не устанавливается (используется ORM-дамп в JSON), так что это
  касается только кастомных установок на хосте.
