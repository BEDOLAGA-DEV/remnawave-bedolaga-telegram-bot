# Переход на PostgreSQL 18

Бот использует PostgreSQL 18 вместо 15. У PostgreSQL 15 поддержка заканчивается
в ноябре 2027 года, у 18 — в ноябре 2030-го.

Данные PostgreSQL 15 нельзя просто открыть в PostgreSQL 18 — их нужно перенести.
Для этого есть команда `make pg-upgrade`: она всё делает сама и ничего не удаляет.

## Новая установка

Ничего делать не нужно: `docker compose up -d` сразу поднимет PostgreSQL 18.

## Обновление существующей установки

В папке бота:

```bash
git pull
make pg-upgrade
```

Если `make` не установлен — `bash scripts/pg-upgrade.sh`.

Скрипт покажет, что собирается сделать, и попросит подтверждения. Бот будет
остановлен на время переноса — обычно это минута-другая, на больших базах дольше.

### Что делает `make pg-upgrade`

1. Проверяет, что места на диске хватит на резервную копию и новую базу.
2. Останавливает бота и базу, чтобы во время переноса никто не писал в базу.
3. Снимает полную резервную копию в `backups/postgres-upgrade-<дата>/` и проверяет,
   что она читается.
4. Запоминает, сколько строк в каждой таблице и какие значения у счётчиков.
5. Разворачивает PostgreSQL 18 в **новом** томе и восстанавливает туда копию.
6. Сверяет строки и счётчики один в один. Если хоть что-то не сошлось — новый
   том удаляется, и всё остаётся как было.
7. Запускает базу на PostgreSQL 18, сверяет данные ещё раз, затем собирает и
   запускает бота (`docker compose up -d --build`).

Старый том с PostgreSQL 15 (`<проект>_postgres_data`) **не удаляется и не меняется**.

Запускать повторно безопасно: если перенос уже сделан, скрипт ничего не трогает.

### Если обновили compose, но не запустили перенос

Бот не запустится, а в логах базы (`docker compose logs postgres`) будет сообщение
с просьбой выполнить `make pg-upgrade`. Это защита: без неё PostgreSQL 18 молча
создал бы пустую базу, и выглядело бы так, будто все данные пропали. Данные при
этом целы — просто выполните `make pg-upgrade`.

## Откат на PostgreSQL 15

Если после перехода что-то не так:

```bash
docker compose down
git checkout <прошлая версия бота> -- docker-compose.yml
docker compose up -d
```

Бот вернётся на старую базу в том виде, в каком она была в момент переноса.
Всё, что изменилось после переноса, при откате не сохранится.

## Когда всё работает

Через неделю-другую, убедившись, что всё в порядке, можно освободить место:

```bash
docker volume rm <проект>_postgres_data      # старая база PostgreSQL 15
rm -rf backups/postgres-upgrade-*            # резервные копии перед переносом
```

Имена тома и папки с копией скрипт печатает в конце работы.

## Для своих установок

- Если у вас свой `docker-compose.yml` или `docker-compose.override.yml`, учтите:
  образ `postgres:18` хранит данные в `/var/lib/postgresql/18/docker`, поэтому том
  монтируется в `/var/lib/postgresql`, а не в `/var/lib/postgresql/data`, как раньше.
  Со старым путём данные окажутся вне тома и пропадут при пересоздании контейнера.
- Если база внешняя (не из нашего compose), скрипт вам не нужен: переносите её
  привычным для вашего хостинга способом. Бот работает и с 15, и с 18.
- В резервной копии лежат хэши паролей ролей базы: папка `backups/` доступна только
  владельцу, не выкладывайте её никуда.
