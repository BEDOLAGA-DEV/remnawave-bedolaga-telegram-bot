# Семейства коммерческих тарифов: подготовка модели данных

## Назначение

`Tariff.entitlement_family` — необязательный строковый идентификатор коммерческого
семейства тарифов. Несколько уровней одной услуги могут иметь одинаковый ключ
(`main`); независимая платная услуга может иметь другой ключ
(`metered_bypass`). Конкретные имена выбирает оператор.

Поле отделено от `tier_level`, `allowed_squads`, промогрупп и Remnawave
идентификаторов: уровень цены и серверная инфраструктура сами по себе не
определяют независимость подписок.

## Совместимость и текущие ограничения

Миграция 0132 добавляет nullable `tariffs.entitlement_family VARCHAR(64)`.
Существующие строки получают `NULL`; новые тарифы без явно переданного
значения тоже получают `NULL`. Формат ключа:
`[a-z][a-z0-9_-]{0,63}`. Административный API возвращает поле в списке
и карточке, принимает при создании и позволяет задать, изменить либо
сбросить (`null`) при редактировании.

**Важно: в этой версии поле — только метаданные.** Оно НЕ меняет
`MULTI_TARIFF_ENABLED`, не скрывает предложения, не запрещает несколько
подписок одного семейства, не влияет на выбор Remnawave пользователя,
действующие ссылки, оплату и автопродление. Нельзя считать назначение
`main` или `metered_bypass` достаточной защитой для коммерческого запуска.

Не назначайте группе смысл по одному UUID сквада, имени тарифа или
`tariff_id`. Переклассификация живого тарифа в будущем потребует проверки
имеющихся подписок и согласованного сценария миграции.

## Следующий этап: runtime-инварианты (не входит в этот PR)

- Один владелец может иметь не более одной живой подписки семейства
  `main`; изменение уровня Main должно сохранять `Subscription.id`,
  Remnawave identity и URL, где upstream поддерживает это.
- При покупке другой независимой услуги может создаваться отдельная
  `Subscription` и отдельный Remnawave identity.
- Все денежные entrypoints (Telegram, Cabinet, Mini App, Web API,
  auto-purchase/recurring) проверяют допустимость операции до списания.
- При конкурентных запросах правило подтверждается PostgreSQL-транзакцией
  или ограничением БД, а не проверкой только на уровне UI.
- Продление своей подписки, trial conversion, switch и админские операции
  имеют собственные правила; существующие оплаты не блокируются
  неявно.
- До включения требуются интеграционные и конкурирующие PostgreSQL-тесты
  и отдельное эксплуатационное разрешение.

Никакого общего ограничения по семействам здесь намеренно не создаётся:
`Subscription` пока хранит только `tariff_id`, а обычный индекс
`(user_id, tariff_id)` не обеспечивает уникальность по семейству через JOIN.
