# Комиссия продавца и доход после комиссии

Комиссия эквайринга настраивается отдельно для **каждого метода каждого провайдера**. Например, СБП и карты у одного шлюза могут иметь разные ставки. Комиссия другого шлюза задаётся независимо.

Настройка не меняет цену, сумму платежа, начисление баланса и стоимость подписки. Это расчёт расходов продавца на приём платежа. Результат не является чистой прибылью: серверы, налоги, возвраты, вывод средств и прочие расходы здесь не вычитаются.

## Настройка через API кабинета

`GET /cabinet/admin/payment-methods` возвращает `merchant_fee_policies` у каждого провайдера. `PUT /cabinet/admin/payment-methods/{method_id}` принимает тот же список; требуются существующие права `payment_methods:edit`.

Пример тела для провайдера с методами `sbp`, `card`, `crypto`:

```json
{
  "merchant_fee_policies": [
    {
      "effective_from": "2025-01-01T00:00:00Z",
      "default": {"percent": "5", "fixed_kopeks": 0},
      "sub_methods": {
        "sbp": {"percent": "2", "fixed_kopeks": 0},
        "card": {"percent": "4", "fixed_kopeks": 100},
        "crypto": {"percent": "1.5", "fixed_kopeks": 0}
      }
    }
  ]
}
```

У Platega ключи методов — строковые числовые коды из `available_sub_options`, например `2` и `11`; у YooKassa `bank_card` приводится к `card`; значения `CARD`/`SBP` приводятся к нижнему регистру. Провайдеры, сохраняющие числовой ID платёжной системы, используют этот ID строкой. Реальные значения присутствуют в разбивке отчёта `sub_method`.

`percent` — от 0 до 100 с точностью до четырёх знаков после запятой; `fixed_kopeks` — фиксированная комиссия с каждой операции. Процент и фиксированная часть складываются; итог округляется до копейки (половина вверх). Фиксированная комиссия может превышать сумму маленького платежа — тогда расчётный доход отрицательный.

Для смены ставки добавьте запись с новой `effective_from`, сохранив старые записи. Время обязательно с часовым поясом, одинаковые даты запрещены. Ставка выбирается по `transactions.created_at`, как и существующие отчёты дохода. Изменение старой записи или удаление списка намеренно пересчитывает историю; это аналитическая конфигурация, а не неизменяемый бухгалтерский реестр фактических удержаний. API заменяет список целиком; обычное редактирование других полей списка комиссий не касается.

До первой настроенной даты комиссия считается неизвестной: сумма остаётся в валовом доходе, а платёж отмечается в `unconfigured_count`. Можно явно задать нулевую ставку, если комиссии нет. При неизвестном методе применяется `default`, а при наличии отдельных ставок растёт `unknown_sub_method_count`. Если `default` не задан и отдельной ставки для метода нет, комиссия тоже считается неизвестной. Определять метод по описанию платежа система не пытается.

## Отчёт

В Telegram: админка → статистика → доходы. Показаны суммы до комиссии, комиссия и расчётный доход после комиссии за месяц и всё время, а также разбивка по провайдеру и его методу.

`GET /cabinet/admin/stats/merchant-revenue?start=...&end=...` доступен с правами `stats:read`. Границы включительные, в формате ISO 8601 с часовым поясом. Результат:

- `gross_kopeks`: поступления до комиссии;
- `fee_kopeks`: расчётная комиссия продавца;
- `net_kopeks`: поступления минус комиссия;
- `count`, `unconfigured_count`, `unknown_sub_method_count`;
- `by_method`: те же показатели по паре `provider` + `sub_method`.

Dashboard дополнен полями `merchant_fee_month_kopeks`, `income_month_after_fee_kopeks`, `merchant_fee_total_kopeks`, `income_total_after_fee_kopeks`, `fee_unconfigured_transactions`. Существующие поля дохода остаются валовыми для совместимости. Поля настройки и отчёта доступны frontend кабинета через API; в этом репозитории нет исходников frontend формы.

В доход включаются только завершённые пополнения и прямые внешние покупки подписок. Оплаты с внутреннего баланса, ручные начисления, неуспешные платежи и возвраты в этот показатель не включаются, как и в прежнем валовом отчёте. Один и тот же платёж не считается второй раз при расходовании баланса.

Для подметода используется только связь записи шлюза с учётной транзакцией. Если шлюз не сохранил метод, записи нет или сведения конфликтуют, значение остаётся неизвестным. Новые шлюзы с полями `payment_method_code`, `payment_method_type`, `payment_method` или `payment_system_id` и связью `transaction_id` подхватываются через общий реестр шлюзов. Для иных моделей нужна отдельная адаптация.

## Обновление

Миграция `0134` добавляет nullable JSON-поле в `payment_method_configs`. Существующие конфигурации и транзакции не меняются. После миграции настройте комиссии; до настройки отчёт явно показывает неподтверждённую комиссию.
