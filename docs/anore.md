# Anore

Интеграция принимает рублёвые платежи через размещённую у Anore платёжную форму (`paymentUrl`). Поддерживаются `sbp`, `card`, `yoomoney`, `crypto`, если они доступны кассе. Локальные суммы хранятся в копейках, в API передаются рубли без округления дробной копейки. USD, выплаты продавцу, автосписания, H2H и собственная карточная форма не реализованы.

Контракт провайдера: [официальная документация Anore](https://anore.cc/docs). Ниже описано поведение этой интеграции, включая более строгие локальные ограничения.

## Настройка

1. Создайте кассу и API-ключ в Anore. Для аккаунтного ключа нужен положительный числовой `ANORE_SHOP_ID`: ключ обслуживает несколько касс. В текущей проверке настройки ключи с префиксом `an_` считаются аккаунтными. Для ключа, привязанного к кассе, идентификатор может не требоваться.
2. Задайте `ANORE_API_KEY` и `ANORE_SECRET_KEY` на сервере. Секрет необходим для проверки webhook, хотя провайдер допускает исходящие запросы только с Bearer-ключом. Интеграция также подписывает исходящие запросы HMAC-SHA256. Секретные поля в админском интерфейсе маскируются; реальные значения не помещайте в репозиторий.
3. Настройте публичный HTTPS-адрес webhook и проксирование к единому HTTP-приложению. **`callbackUrl` собирается из `WEBHOOK_URL` с добавлением `ANORE_WEBHOOK_PATH`**, с нормализацией разделительного `/`. Например, `WEBHOOK_URL=https://invalid.example` и путь `/anore-webhook` дают `https://invalid.example/anore-webhook`. Это пример, не рабочий адрес. Если `WEBHOOK_URL` пуст, `callbackUrl` в запрос создания не передаётся: адрес доставки нужно обеспечить на стороне кассы.
4. Перезапустите приложение после первоначального добавления реквизитов или изменения пути webhook: маршруты регистрируются при старте.
5. Проверьте эффективные настройки и доступность методов в админке. Включите `ANORE_ENABLED` после подготовки кассы и доставки webhook.

По умолчанию шлюз выключен. Наличие реквизитов (`is_anore_configured`) и разрешение новых платежей (`is_anore_enabled`) разделены: при настроенных реквизитах webhook регистрируется даже с `ANORE_ENABLED=false`. Отключение новых счетов не прекращает обработку уже выданных.

| Настройка | Значение по умолчанию / назначение |
| --- | --- |
| `ANORE_ENABLED` | `false` |
| `ANORE_DISPLAY_NAME` | `Anore` |
| `ANORE_API_URL` | `https://api.anore.cc/v1` |
| `ANORE_API_KEY` | Обязательный серверный ключ |
| `ANORE_SECRET_KEY` | Обязательный секрет подписи |
| `ANORE_SHOP_ID` | Положительный ID кассы для аккаунтного ключа |
| `ANORE_PAYMENT_METHODS` | `sbp,card,yoomoney,crypto` |
| `ANORE_MIN_AMOUNT_KOPEKS` | `10000` (100 ₽) |
| `ANORE_MAX_AMOUNT_KOPEKS` | `100000000` (1 000 000 ₽) |
| `ANORE_REQUEST_TIMEOUT` | `30` секунд |
| `ANORE_WEBHOOK_PATH` | `/anore-webhook` |
| `ANORE_SUCCESS_URL`, `ANORE_FAIL_URL` | Не заданы; вызывающий сценарий может передать адрес возврата |

Минимум и максимум — редактируемая политика приложения, а не заявленные лимиты Anore. Платёжная форма может дополнительно ограничивать доступные кассе суммы и способы.

Настройки из БД могут переопределять `.env`. В конфигурации способа `anore` учитываются включение, суммы, подметоды, тип пользователя, первое пополнение и промогруппы. Проверка выполняется на сервере при создании счёта, включая Telegram и гостевые вызовы. Общая форма получает только разрешённые подметоды; выключение всех подметодов скрывает шлюз, а не открывает неограниченную форму. Гостю нельзя доказать ограничения по аккаунту/промогруппе/первому пополнению, поэтому такие конфигурации ему недоступны. Новые ограничения не применяются задним числом к уже выданному счёту при подтверждении оплаты.

## Сценарии покупки

- Telegram, кабинет и Mini App: пополнение баланса, история и штатная ручная/фоновая проверка.
- Сохранённая корзина: оплата зачисляется на баланс; продолжение покупки запускает существующий механизм обработки корзины.
- Гостевая покупка и подарок: связь с покупкой сохраняется до обращения к провайдеру. После подтверждения факт оплаты платежа и покупки фиксируется атомарно, затем выполняется выдача. Подарок остаётся в штатном сценарии получения по ссылке; подтверждение платежа не выдаёт его произвольному аккаунту.
- Простая подписка и платный триал: кнопка Anore явно предлагает **пополнить баланс**. Затем пользователь возвращается к покупке подписки или активации триала за баланс. Прямой автоматической покупки из FSM простой подписки и активации триала этим шлюзом нет.

## Подтверждение и повторная доставка

Webhook принимает исходное тело размером не более 64 КиБ. `Anore-Signature` проверяется как hex HMAC-SHA256 точных байтов тела. Нужны также `Anore-Event` и непустой `Anore-Delivery-Id` длиной до 128 символов. Заголовок события должен совпадать с подписанным `event` в JSON; одного заголовка недостаточно для начисления.

`payment.succeeded` и `payment.expired` проверяются по локальному заказу, ID провайдера, точной сумме, валюте и статусу. События выплат не начисляют баланс. Ручная проверка сначала проверяет принадлежность платежа пользователю. Повторы и конкурентные подтверждения сходятся в одну обработку с блокировками и атомарной записью платежа, баланса и транзакции.

HTTP 2xx означает долговечное принятие события, а не завершение доставки подписки в панель. Неверная подпись получает 401, некорректное тело/событие или несоответствующий платёж — 400, превышение размера — 413; неизвестный локальный заказ — 400; временный сбой обработки — 500 для повторной доставки. Корректный повтор уже принятого платежа не начисляет деньги второй раз. Поздний `expired` не отменяет принятую оплату.

Уведомления, реферальная обработка и продолжение корзины выполняются после финансового commit через существующие механизмы. Их сбой не откатывает начисление; гарантия ровно одной внешней отправки или выполнения после падения процесса не заявляется. Гостевая выдача после долговечного принятия использует штатный повтор для оплаченных, но ещё не выданных покупок.

## Неопределённый результат создания и проверки статуса

Локальная запись платежа и ожидающая гостевая покупка фиксируются **до POST**. Поэтому callback, пришедший раньше ответа создания, сохраняет связь с заказом. Запоздалый ответ не перезаписывает уже принятую оплату.

После timeout, сетевого сбоя или некорректного ответа создания автоматически повторять POST нельзя: провайдер мог создать счёт. Локальный заказ остаётся для восстановления через webhook. Если ID провайдера ещё неизвестен, приложение не опрашивает его по вымышленному ID и не сканирует все счета кассы. Не считайте сообщение об ошибке создания доказательством отсутствия счёта; при разборе сверяйте локальный `order_id` с данными кассы, не начисляя деньги вручную без подтверждения.

GET статуса выполняется не чаще одного раза в три секунды на платёж. Резерв времени хранится в БД и сохраняется при неудачном запросе; более долгий `Retry-After` увеличивает отсрочку. Документированные состояния отдельного платежа: `new`, `paid`, `expired`. Обычно счёт действителен четыре часа; приложение сохраняет `expiresIn` из ответа, используя 14400 секунд при его отсутствии. Истечение времени само по себе не является подтверждением оплаты.

## Sandbox и смена реквизитов

Ключ с префиксом `an_test_` помечает каждый созданный счёт как тестовый. Флаг хранится на платеже и не меняется при последующем переключении ключа. Тестовая оплата не начисляет баланс, не создаёт платную выдачу и исключается из восстановления оплаченных гостевых покупок и финансовой статистики. Наличие тестового подтверждения не доказывает работу реального эквайринга.

Перед сменой кассы, API-ключа или секрета завершите/разберите открытые счета. Исходящие параметры фиксируются для конкретного создания, но старые секреты не сохраняются: после ротации новый секрет не проверит старую подпись, а новый аккаунтный ключ может не видеть прежние счета. Бесшовная ротация реквизитов не поддерживается. Это отличается от простого отключения `ANORE_ENABLED`, которое сохраняет возможность принять старую оплату.

## Проверки перед эксплуатацией

Автоматические локальные проверки используют синтетические данные и локальный HTTP-сервер/тестовую БД. Внешняя sandbox-оплата Anore и доставка webhook от реального провайдера при разработке не проверялись. Перед включением реального приёма подтвердите на своей тестовой кассе доступность callback, подпись, выбранные методы, возврат из формы и отсутствие начисления тестового счёта. Не используйте production-БД для тестового прогона приложения.
