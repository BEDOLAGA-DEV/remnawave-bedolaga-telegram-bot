# Subscription Link Domain Override — Design

**Date:** 2026-06-21
**Status:** Approved (design) — pending spec review

## Problem

Subscription links are issued with the RemnaWave panel host, e.g.
`https://users.sbp1.not.virtualsprivate.network/KC8QUowCXvXSkt...`.

The operator wants to set, in the bot admin panel, a replacement domain. After
that, **everywhere** a subscription link is issued, the panel host is swapped
for the configured host. The old panel host may be unreachable (blocked), so the
replacement must work end-to-end — including the encrypted Happ crypt5 link the
client actually fetches.

A secondary defect: some surfaces emit the raw `subscription_url` directly,
bypassing the central display helper, so the plain link "leaks" even in
crypto-link mode. These must be unified onto the display helper.

## Decisions (from brainstorming)

1. **Scope:** everywhere — Telegram bot, mini app, web cabinet, REST API,
   happ-scheme / crypto / redirect links.
2. **Admin input:** a single field — the new domain. Surfaces automatically in
   the existing admin "Подписки и лимиты" menu via `BotConfigurationService`.
3. **Replacement:** override the host (netloc) of links. The stored
   `subscription.subscription_url` is **never mutated** (it is authoritative for
   panel sync / matching). Plain links are overridden **on read**.
4. **Plain-leak fix:** unified crypt behavior — bot/cabinet surfaces that emit
   raw `subscription_url` route through `get_display_subscription_link`. REST API
   keeps both fields (`subscription_url`, `subscription_crypto_link`) but applies
   the domain override to the plain field.
5. **crypt5 vs crypt4:**
   - **crypt5** (`happ://crypt5...`, generated by us via `crypto.happ.su`) is the
     primary displayed crypto link. When an override is active it is
     **regenerated from the overridden URL**, ignoring the panel-provided
     `cryptoLink`.
   - **crypt4** (panel `/api/system/tools/happ/encrypt` fallback, reached only by
     the manual "link broken" button) is **left untouched** (old host acceptable).
6. **Existing subscriptions on domain change:** auto background regeneration of
   crypt5 immediately when the admin saves a new domain (throttled, because
   `crypto.happ.su` is an external service).

## Architecture

### Non-goals / invariants
- Never write an overridden host into `subscription.subscription_url`.
- Internal paths (panel sync, webhook matching, pushing `subscriptionUrl` to the
  panel) keep using the **original** stored URL.
- Display/emit helpers stay **synchronous** (keyboard builders call them sync).
  All remote crypt5 generation happens in async storage/regeneration paths and
  is persisted, so reads are cheap.

### Components

**1. Config + admin (config.py / system_settings_service.py)**
- New setting `SUBSCRIPTION_DOMAIN_OVERRIDE: str | None = None`.
- Category mapping so it appears under `SUBSCRIPTIONS_CORE` ("Подписки и лимиты").
- Getter `settings.get_subscription_domain_override() -> str | None`:
  - Strip/normalize input. Accept `https://my.com/`, `my.com`, `my.com:8443`;
    reduce to a netloc (`host[:port]`). Empty/whitespace → `None`.
  - If the value cannot be parsed into a host, log a warning and return `None`
    (treated as "no override"). No heavy validation (YAGNI).

**2. Plain override helper (app/utils/subscription_utils.py) — sync**
```python
def apply_subscription_domain_override(url: str | None) -> str | None
```
- No override, no url, or url has no netloc → return unchanged.
- Otherwise `urlparse` → replace `netloc` with the configured host →
  `urlunparse`. Scheme / path / query / fragment preserved. Works for both
  `https://host/...` and `happ://host/...`.

**3. crypt5 storage resolver (services layer) — async**
```python
async def resolve_crypto_link_for_storage(subscription_url, panel_crypto_link) -> str | None
```
- Override inactive → return `panel_crypto_link` (current behavior).
- Override active + `subscription_url` present →
  `encrypt_happ_crypto_link(apply_subscription_domain_override(subscription_url))`.
  On encryption failure → fall back to `panel_crypto_link`.
- Wired into every site that currently assigns
  `subscription.subscription_crypto_link = updated_user.happ_crypto_link` (and
  equivalents): `subscription_service.py` (≈262/688/1147/1585),
  `monitoring_service.py` (≈555), `remnawave_webhook_service.py` (≈1248/1496),
  `remnawave_service.py` (≈1934/1973/2081/2239/3163). Sites that explicitly clear
  the link (`= '' / None`) are left as-is.

**4. Background regeneration on domain change**
- Hook fired when `SUBSCRIPTION_DOMAIN_OVERRIDE` changes via the admin
  settings service.
- Background task `regenerate_crypto_links_for_override()`:
  iterate active/trial subscriptions with a `subscription_url`; for each set
  `subscription_crypto_link = await resolve_crypto_link_for_storage(...)`;
  throttle (small delay / batching) to be gentle on `crypto.happ.su`; commit in
  batches; log progress and failures (failures keep the old link).

**5. Emit points**
- `get_display_subscription_link` (sync):
  - crypto mode → return stored `subscription_crypto_link` (already the
    overridden crypt5).
  - otherwise → `apply_subscription_domain_override(base_link)`.
- **Plain-leak fixes → route through `get_display_subscription_link`:**
  - `handlers/subscription/my_subscriptions.py` (~256): replace raw
    `subscription.subscription_url` block.
  - cabinet `subscription_modules/status.py` (~144/414), `multi_tariff.py` (~67),
    `helpers.py` (~238); `cabinet/routes/landing.py` (~197);
    `services/guest_purchase_service.py` (~975).
- **REST API → keep both fields, override the plain one:**
  - `webapi/routes/subscriptions.py` (~64), `users.py` (~84),
    `_subscription_state.py` (~23), `miniapp.py` (~2895/3360):
    `subscription_url` passed through `apply_subscription_domain_override`;
    `subscription_crypto_link` already overridden at storage.
- **Derived links** (happ-scheme conversion, redhash, redirect template) are
  always built from `get_display_subscription_link` output (or an
  override-applied URL), never from the raw stored `subscription_url`. The
  implementation audit confirms each builder's input.

### Data flow

Issue plain link → read stored `subscription_url` → `apply_..._override` → emit.
Issue crypto link → read stored `subscription_crypto_link` (overridden crypt5
baked at storage / regenerated on domain change) → emit.
Panel sync → writes original `subscription_url`; crypt5 re-derived via
`resolve_crypto_link_for_storage` so steady state stays overridden.

### Error handling
- Override unset/blank → zero behavior change anywhere.
- crypt5 encryption failure → fall back to panel crypto link (never crash an
  emit path); logged.
- URL with no host (opaque/empty) → returned unchanged.

## Testing

- Unit `apply_subscription_domain_override`: https, `happ://`, with port, empty,
  no-netloc, override unset.
- Unit getter normalization: scheme/path/port/trailing-slash/blank → host.
- Unit `resolve_crypto_link_for_storage`: override on/off, encrypt-failure
  fallback.
- Unit `get_display_subscription_link`: {crypto, plain} × {override on, off}.
- Regression: a representative plain-leak emit point now returns the display
  link in crypto mode.

## Out of scope (YAGNI)
- Per-user / per-tariff domains (single global override only).
- Rewriting the crypt4 panel fallback link.
- Manual "regenerate" admin button (auto background covers it).
