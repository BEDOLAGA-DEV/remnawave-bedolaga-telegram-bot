# Main-family XOR: серверный контракт и план внедрения

> Статус: проектирование, не включать в production. Зависимость: #3332 (необязательное `Tariff.entitlement_family`); не относится к фиксу промогрупп #3331 и тесту README #3321.

## Цель и границы

При `MULTI_TARIFF_ENABLED=true` разрешить одному аккаунту не более одной **живой** подписки каждого явно указанного коммерческого семейства (`main`, `metered_bypass` и др.). В частности:

- `Main / Start` → `Main / Standard`: **смена тарифа той же подписки**, а не новая запись и новый Remnawave user.
- `Main + metered_bypass`: две отдельные подписки и две независимые Remnawave identities/квоты.
- `NULL` у тарифов, созданных ранее: существующее поведение без новой политики; неизвестное семейство **не следует угадывать по squad, имени или tier**.
- В однотарифном режиме существующая логика не меняется.
- Публичные продажи и миграция действующих тарифов в `main` отдельно контролируются оператором; эта задача сама по себе не включает multi-tariff.

## Семантика

1. «Живая» означает статус `active`, `trial` или `limited`: такой же набор используется в частичном уникальном индексе `uq_subscriptions_user_tariff_active`. Истёкшие/выключенные строки не занимают живое место. Конверсия пробной подписки и возврат из expired рассматриваются как изменения существующей записи.
2. У одной записи при смене тарифа не меняются `Subscription.id`, `remnawave_id` и, без отдельного обоснования, `subscription_url`. Изменяются тарифные параметры и разрешённые squads согласно имеющемуся upstream switch flow. Проект учитывает #3309, не копируя её реализацию.
3. Новая покупка тарифа того же явно заданного семейства, если уже существует другая живая подписка, **отклоняется до платежа** с машиночитаемой причиной «смените тариф существующей подписки». Не создавать вторую Main запись и не выполнять автоматическое незаявленное переключение.
4. Продление именно этой подписки допустимо; повторная покупка её текущего тарифа обрабатывается как существующее продление, а не семейный конфликт.
5. Изменения семейства в админке не должны молча создавать нарушения у существующих живых записей. Возможны только атомарный согласованный перенос с проверкой или безопасный отказ. Массового заполнения `NULL` миграцией нет.

## Конкурентная безопасность и транзакции

Один `SELECT` до записи не защищает от одновременных покупок. Запрет должен выдерживать гонку двух транзакций, покупающих **разные тарифы одного семейства**.

Выбранная для PostgreSQL реализация DB-инварианта (миграция `0133`, код в `app/database/tariff_family_schema.py`):

- `BEFORE INSERT / UPDATE` подписки читает семейство из `Tariff` с `FOR SHARE`, берёт транзакционную advisory-блокировку по `(user_id, hashtext(family))` и повторно проверяет существующие live-подписки. Конкурирующая вставка другого Main должна дождаться исхода первой транзакции и получить SQLSTATE `23505`, если семейство уже занято.
- `AFTER UPDATE` семейства тарифа проверяет живые подписки затронутых аккаунтов в упорядоченном цикле; нельзя превратить существующие legacy-подписки в конфликтующие Main одним изменением метаданных.
- Выбранный механизм рассчитан на PostgreSQL `READ COMMITTED` — этот уровень изоляции явно используется приложением в `app/database/database.py`. Гарантии для `REPEATABLE READ` пока не доказаны; при другой изоляции нужна отдельная защита либо запрет операции. SQLite эту PostgreSQL-гарантию **не** предоставляет.
- На пустой PostgreSQL-схеме триггеры устанавливаются через `Base.metadata.create_all`; на существующей — миграцией `0133`. Миграция блокирует конкурирующие записи на время установки и отказывает при найденных агрегатных конфликтах без раскрытия пользовательских ID.

Это **только последний барьер в БД** и он ещё требует прохождения PG15/PG18 CI и независимого ревью. На уровне бизнес-логики по-прежнему обязательны:

- Общая family-policy **до** списания, промоакции, создания финансового документа и внешнего необратимого эффекта во всех публичных entrypoints.
- Блокировка родительской строки `User` через существующий `lock_user_for_pricing`/аналог до перечитывания подписок; удерживать блокировку до атомарного `COMMIT` финансовой операции и создания подписки. Существующий `subtract_user_balance(commit=True)` до вставки эту гарантию разрушает.
- Обработчик конфликтов обязан объяснять пользователю «смените тариф существующей подписки» и **не оставлять списание без подписки**. PostgreSQL после `IntegrityError` требует rollback.
- Смена тарифа, revive и конверсия триала должны сохранять исходные Remnawave identities и проверяться на действующих upstream-контрактах, включая #3309.

До выполнения этих пунктов эксплуатационное включение `Main-family XOR` запрещено.

## Контрольная матрица

| Сценарий | Ожидание |
|---|---|
| Без семейства (`NULL`) | Совместимое legacy-поведение |
| Нет живого `main`, покупка `Main A` | Одна новая подписка |
| Живой `Main A`, покупка `Main B` | Отказ **до** оплаты, предложение switch |
| Живой `Main A`, его продление | Разрешено, identity не меняется |
| Живой `Main A`, покупка `metered_bypass` | Независимая вторая identity |
| Живой `main` trial → платный `main` | Конверсия на месте без второго live `main` |
| Expired `Main A` и новая покупка | Корректный revive либо новая строка без двух live |
| Два конкурентных запроса `Main A` и `Main B` | Не более одного live `main`, финансовый результат согласован |
| Смена семейства тарифа в админке | Не создаёт конфликт; отказ или атомарное безопасное изменение |
| Откат после неудачного Panel API | Нет «платёж без продукта»; rollback/компенсация проверены |

## Проверки для готовности к ревью

1. Тест на **реальном PostgreSQL**, воспроизводящий конкурентную покупку разных тарифов `main`, с явной синхронизацией участников и проверкой финансового итога.
2. Тест на обычную покупку, продление, switch (включая #3309), trial conversion, revival, отключение/истечение, редактор семейства, чужое семейство и legacy `NULL`.
3. Обход всех путей: Telegram, Cabinet, Mini App, Web API, автопокупка, guest/coupon/referral/callback, админка. Для каждого — policy перед финансовым эффектом.
4. Проверки `ruff`, полный `pytest` PG15/PG18, миграция upgrade/downgrade и независимое ревью. Не смешивать результаты разных SHA.
5. Отдельно подтвердить устранение baseline `paypear` через #3321 в `dev`; не переносить чужой fix в этот PR.
6. До открытия Gate A Flexus #291 нужны operator-only read-only preflight, отдельное разрешение на тарифы/режим и штатный rollback. Даже успешный upstream CI не подтверждает работоспособность production.
